# 高德周边地点推荐

根据用户所在位置与需求，查询真实的高德 POI 与步行路线，返回**最多 3 个**从同一起点出发、可在步行时间上限内到达的候选地点。

本 Skill 只做一次「提出需求 → 查询高德 → 返回推荐」。不涉及长期记忆、多轮反馈、跨城市经验迁移，也不接入 PowerMem / seekdb。

## 何时使用

用户表达的是「从某个位置出发，找某类可达地点」的诉求，例如：

- 「我在杭州某地铁站，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。」
- 「公司附近有适合吃午饭的地方吗，走过去 10 分钟内」
- 「附近有什么公园可以散步」

不适用：需要实时路况、多段行程编排、驾车/公交导航、或与地理无关的问答。

## 工具

使用宿主目录中实际暴露的高德 MCP 工具。官方 MCP Server 的规范工具名如下（宿主可能带命名空间前缀，例如 `amap-maps.maps_around_search`，以宿主目录中的实际名称为准）：

| 工具 | 作用 | 必填参数 | 可选参数 |
| --- | --- | --- | --- |
| `maps_around_search` | 周边搜索：按关键词 + 中心点坐标搜 POI | `location`（中心点经度纬度，`"经度,纬度"`） | `keywords`、`radius`（米，默认 `1000`，取值 0–50000） |
| `maps_text_search` | 关键词搜索：按关键词在指定城市搜 POI | `keywords` | `city`、`citylimit` |
| `maps_search_detail` | POI 详情：按 POI ID 取坐标、地址、类型 | `id` | — |
| `maps_direction_walking` | 步行路径规划：起终点坐标 → 步行距离与耗时 | `origin`、`destination`（均为 `"经度,纬度"`） | — |
| `maps_geo` | 地理编码：结构化地址 → 坐标 | `address` | `city` |
| `maps_regeocode` | 逆地理编码：坐标 → 省市区 | `location` | — |

工具不可用时，指出它的准确名称与失败原因，不要用其他工具臆造同类结果。

### 返回字段与单位

- `maps_around_search` / `maps_text_search` 返回 `pois[]`，每项含 `id`、`name`、`address`、`typecode`。**不含坐标**。
- `maps_search_detail` 返回 `id`、`name`（地点名）、`location`（**地点经纬度**，`"经度,纬度"`）、`address`（地址）、`city`、`business_area`（商圈）、`type`（完整类型路径，如 `餐饮服务;咖啡厅`）、`alias`、`photos`，以及 `biz_ext` 内的 `rating`、`cost` 等扩展字段（可能为空）。
- `maps_direction_walking` 返回 `route.paths[]`，每项含 `distance`（**单位：米**）、`duration`（**单位：秒**）、`steps[]`（每段 `instruction`、`road`、`distance`、`duration`）。取 `paths[0]` 作为该起终点的步行方案；`paths` 为空表示未规划出路线。
- `address`、`alias` 等字段在无值时可能返回空数组而非空字符串，按缺失处理。
- `biz_ext.rating`、`biz_ext.cost` 常为空数组，不足以支撑任何结论。

## 执行流程

### 1. 解析用户输入

从用户原话中提取以下要素；缺失项按「默认」处理，冲突项以用户显式表述为准。

| 要素 | 取值 | 缺省 |
| --- | --- | --- |
| 城市 | 城市名，用于关键词搜索限定 | 用户未提则不限定城市 |
| 起点 | 坐标或地名 | 必须有；无坐标时用 `maps_geo` 解析 |
| 地点类型/需求 | 咖啡馆、餐厅、公园、超市… | 必须有；无类型则询问用户 |
| 步行时间上限 | 分钟 | 用户未提则不设上限 |
| 推荐数量 | N | 3，且最终结果不得超过 3 |
| 排序偏好 | 如「优先近一点」 | 无偏好则按步行时间由近到远 |

用户未给起点坐标但给了地名（如「杭州某地铁站」）时，用 `maps_geo` 把地址解析成坐标；地名模糊到无法唯一定位时，先向用户确认，不要随便取一个同名地点。

### 2. 检索候选地点

用 `maps_around_search`，`location` 传起点坐标，`keywords` 传地点类型词。

`radius` 只是**候选检索范围**，不作为推荐里的步行距离。按步行时间上限取一个略宽的半径（可多给余量，圆形检索比实际路径更紧凑）：

| 步行上限 | 建议 radius |
| --- | --- |
| 5 分钟 | 800 |
| 10 分钟 | 1200 |
| 15 分钟 | 1800 |
| 20 分钟 | 2400 |
| 30 分钟 | 3500 |

未设步行上限时用 `2000`。半径取值上限为 `50000`。

候选池要够筛：单次周边搜索最多返回约 20 条。返回过少时，先加大 `radius`，再换用同义关键词（如「咖啡馆」与「咖啡厅」）重搜。

周边搜索无结果时，改用 `maps_text_search`（`keywords` + `city`）扩大范围，拿到的候选仍需按第 3 步定位坐标后再走第 4 步。

### 3. 核对类型并取坐标

对候选逐个调用 `maps_search_detail(id)`，取得 `location` 与 `type`。

- **类型筛选**：只保留 `type` 与用户所需类别一致的地点（如用户要咖啡馆，`type` 应落在餐饮服务下的咖啡厅一类）。`typecode` 的前两位代表同一大类，可作粗筛，但以 `type` 字符串为准。类型明显不符的候选直接排除，不进入推荐。
- **坐标来源**：`maps_around_search` 与 `maps_text_search` 都不返回坐标，**必须**通过 `maps_search_detail` 拿到 `location` 才能规划步行路线。
- `maps_search_detail` 调用失败或没有 `location` 的候选，无法进入下一步。

### 4. 逐个查询步行路线

对每个通过类型筛选且有坐标的候选，调用 `maps_direction_walking`：

- `origin` **始终是用户指定的同一个起点坐标**。
- `destination` 是该候选自己的 `location`。
- 每个候选各自单独调用一次，得到的是「起点 → 该候选」的一条独立路线。**不要把多个地点串成一条路线**，它们是同一起点下的并列备选。

读取 `route.paths[0].distance`（米）与 `route.paths[0].duration`（秒）。`paths` 为空或调用报错时，该候选**无法确认步行耗时**，不得当作满足时间要求。

### 5. 筛选

- 用户设了步行时间上限时：`duration`（秒）必须 ≤ 上限（分钟）× 60。超时的候选一律不进推荐列表，即使它类型匹配、距离很近。
- 路线查询失败或缺数据的候选，不进推荐列表。
- 推荐数量 ≤ 用户要求的 N，且 ≤ 3。

### 6. 排序

- 「优先近一点」「最近」等偏好：按 `duration` 升序排列（与实际步行路线一致）；`distance` 同步作为参考。
- 其他明确偏好（如评分、品类细分）优先于距离排序，但**不得违反步行时间上限**。可用的偏好依据只能来自工具返回字段（如 `biz_ext.rating` 非空时才可引用）。
- 用户未表达偏好时，按 `duration` 升序。

### 7. 生成回答

按第「回答格式」输出。每条推荐都要能追溯到工具返回的名称、地址、坐标与路线数据。

## 硬性约束

1. **步行距离与时间必须来自 `maps_direction_walking` 的路线结果**。不得用直线距离、坐标差、地图目测、经验速度换算或任何估算值替代。
2. **不得用 `maps_distance` 的直线距离测量（`type=0`）冒充步行路线数据**；`maps_distance` 的步行测量也不作为推荐里的距离与耗时来源。
3. **每个候选的路线都必须从同一个用户起点出发**，一次调用只对应一个候选终点。
4. **不得推荐步行时间超出用户上限的地点**。不确定耗时（路线失败/缺数据）的地点不进入符合条件推荐列表。
5. **推荐数量不得超过 3 个，也不得超过用户指定的数量**。
6. **地点名称、地址、类型只能来自工具返回**。不得编造、合并或改写地点；不得用记忆里的常识地点替代查询结果。
7. **推荐理由必须能从地点信息或路线数据推出**（如「步行约 6 分钟、480 米，是筛选后最近的咖啡馆」「位于 <商圈>」）。无依据的评价不写。
8. 起点与终点的坐标顺序是**经度在前、纬度在后**。直接复用工具返回的 `location` 字符串，不要自行拼接或翻转。
9. 不得凭记忆或推测补充工具未返回的事实（营业中、排队少、安静、评分高等）。

## 异常与缺失处理

| 情况 | 处理方式 |
| --- | --- |
| 周边/关键词搜索失败 | 说明「高德地点搜索服务调用失败」并给出工具名与错误信息，不给出任何地点 |
| `maps_search_detail` 失败 | 该候选排除；若因此候选不足，在结果中说明部分候选详情未能获取 |
| 步行路线查询失败或 `paths` 为空 | 该候选排除，并在结果中说明「该地点的步行耗时未能核实」，不得估算 |
| 步行上限内无符合条件的地点 | 如实说明在当前起点与时间上限内没有查到符合条件的地点，并建议放宽时间上限、扩大半径或换用更宽的品类关键词 |
| 实际找到数量少于用户要求 | 说明实际找到的数量与原因（受时间上限或搜索范围限制），不要凑数 |
| 类型不匹配 | 排除；类型筛选后无合格地点时如实说明 |
| 安静程度、排队情况、营业状态、评分等无数据 | 明确标注「未核实」；`biz_ext.rating`、`biz_ext.cost` 为空数组时同样标注「未核实」，不得给出具体数值或结论 |

「未核实」用于一切工具没有返回的事实性描述，而不是用于表达不确定性或态度。

## 回答格式

先给一句话结论，再给推荐列表，最后按需补充说明。

```
按你的要求（步行不超过 {上限} 分钟，{类型}），找到 {数量} 个可选地点：

| # | 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- | --- |
| 1 | {name} | {address} | {distance} 米 | {duration} 分钟 | {理由} |
| 2 | {name} | {address} | {distance} 米 | {duration} 分钟 | {理由} |
| 3 | {name} | {address} | {distance} 米 | {duration} 分钟 | {理由} |

{补充说明：数量不足 / 排除原因 / 未核实项 / 放宽建议}
```

要求：

- 距离写米（如 `480 米`），超过 1000 米可写 `1.2 公里`。
- 时间由 `duration` 秒换算为分钟，保留一位小数或取整，保持与工具数据一致。
- 表格后只写与本次结果有关的补充说明。全部满足时不必加额外段落。
- 未核实项在对应地点行内或表格后统一标注「未核实」，例如「营业状态：未核实」。
- 语气直接，给出可执行的选择依据，不复述工具调用过程，也不输出工具调用日志或 JSON。

## 最小可用示例

用户：「我在杭州武林广场，想找咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点。」

1. `maps_around_search(location=<武林广场坐标>, keywords="咖啡馆", radius="1800")` → 得到候选 `pois[]`。
2. 对每个候选 `maps_search_detail(id)` → 取 `location` 与 `type`，剔除 `type` 不属咖啡类的。
3. 每个候选各调用一次 `maps_direction_walking(origin=<武林广场坐标>, destination=<该候选 location>)` → 各自得到 `distance` 与 `duration`。
4. 筛掉 `duration > 900` 秒的候选；剩余按 `duration` 升序取前 3 个。
5. 按上表输出名称、地址、距离、时间与基于路线数据的理由。
